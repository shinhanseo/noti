# 알림 중요도 데이터셋 v0.2 설계

## 1. 목적

v0.2는 `noti.`의 규칙 기반 판정만으로 결론 내리기 어려운 알림을 보조 판정하기 위한 데이터셋이다.

모델은 모든 알림을 분류하지 않는다. 다음 조건을 만족하는 알림만 실제 추론 대상이다.

```text
사용자 강제 판정이 없음
규칙 점수 25~39점
규칙 등급 REVIEW
```

따라서 v0.2의 주 학습·평가 데이터도 REVIEW 구간을 중심으로 구성한다. 인증번호처럼 규칙만으로 이미 `IMPORTANT`가 되는 알림이나 명백한 광고처럼 이미 `GENERAL`이 되는 알림은 모델 동작 확인용 보조 데이터로만 사용한다.

## 2. 모델이 예측할 대상

모델이 예측하는 것은 개인의 모든 취향이 아니라 다음 질문에 대한 일반화 가능한 답이다.

> 이 알림을 가까운 시간 안에 확인하거나 행동하지 않으면 사용자가 불이익 또는 중요한 기회 손실을 겪을 가능성이 높은가?

`label`의 의미는 다음과 같다.

| label | 이름 | 기준 |
|---:|---|---|
| 1 | `PROMOTE` | REVIEW 알림을 `IMPORTANT` 쪽으로 올릴 근거가 충분함 |
| 0 | `KEEP` | 즉시 확인할 필요가 부족하여 REVIEW 또는 GENERAL에 유지하는 편이 적절함 |

개인 관계, 관심사, 직업처럼 알림 문장만으로 판단할 수 없는 사례는 억지로 평균 라벨을 붙이지 않는다. `clarity=CONTEXT_DEPENDENT`로 분리하고 기본 학습에서는 제외한다.

사용자가 지정한 중요 앱, 중요 키워드 및 앱별 제외 키워드는 모델 라벨보다 항상 우선한다.

## 3. 라벨 판정 기준

### `PROMOTE`로 분류하는 경우

다음 중 하나 이상이 문장에 구체적으로 드러나야 한다.

- 가까운 기한 안에 제출, 승인, 회신, 납부 또는 참석이 필요하다.
- 결제, 예약, 계정, 배송 등에 사용자의 확인이나 조치가 필요한 예외 상황이 발생했다.
- 일정 시작 또는 변경이 임박했고 놓쳤을 때 복구 비용이 크다.
- 실제 금전 손실, 계정 접근 문제 또는 예약 실패로 이어질 가능성이 있다.
- 사용자가 기다리는 거래나 서비스의 핵심 상태가 변경되었다.

### `KEEP`으로 분류하는 경우

- 광고, 할인, 쿠폰, 추천 또는 참여 유도이다.
- 단순 소식, 콘텐츠 업데이트, 활동 요약 또는 일반 상태 안내이다.
- 마감·시간 표현이 있어도 놓쳤을 때 불이익이 없는 홍보성 문구이다.
- 행동을 유도하지만 구매, 조회, 방문처럼 선택적인 행동이다.
- 구체적인 조치나 불이익이 드러나지 않는다.

### `CONTEXT_DEPENDENT`로 분리하는 경우

- 발신자를 알 수 없는 개인 메시지
- 가족·친구·직장 관계에 따라 중요도가 바뀌는 대화
- 사용자의 관심 분야에 따라 달라지는 공연, 스포츠, 커뮤니티 소식
- 개인이 설정한 운동, 독서, 습관 리마인더

이 데이터는 별도의 문맥 평가 세트로 유지하며 정확도 계산에는 바로 사용하지 않는다.

## 4. CSV 스키마

| 컬럼 | 형식 | 학습 입력 | 설명 |
|---|---|---|---|
| `id` | 문자열 | 아니오 | 데이터 행 고유 ID |
| `app_name` | 문자열 | 기본 제외 | 알림을 보낸 앱의 표시 이름 |
| `package_name` | 문자열 | 아니오 | Android 패키지명. 앱 연동 검증용 |
| `title` | 문자열 | 예 | 실제 알림 제목. 앱 이름만 오는 경우도 허용 |
| `body` | 문자열 | 예 | 실제 알림 본문 |
| `label` | `0`, `1`, 빈 값 | 정답 | `KEEP=0`, `PROMOTE=1`, 문맥 의존은 빈 값 |
| `notification_type` | 문자열 | 아니오 | 거래, 배송, 일정, 광고 등 의미 유형 |
| `template_group` | 문자열 | 아니오 | 유사 문장 템플릿을 묶는 분할 단위 |
| `clarity` | 문자열 | 아니오 | `CLEAR` 또는 `CONTEXT_DEPENDENT` |
| `reason_code` | 문자열 | 아니오 | 라벨을 부여한 핵심 근거 |
| `android_category` | 문자열 | 기본 제외 | Android 알림 카테고리 |
| `is_ongoing` | 불리언 | 기본 제외 | 진행 중 알림 여부 |
| `rule_score` | 정수 | 아니오 | 현재 규칙 엔진이 계산한 점수 |
| `rule_level` | 문자열 | 아니오 | 규칙만 적용한 `IMPORTANT`, `REVIEW`, `GENERAL` 등급 |
| `forced` | 불리언 | 아니오 | 사용자 설정으로 판정이 강제되었는지 여부 |
| `model_eligible` | 불리언 | 필터 | 강제 판정이 없고 규칙 점수가 25~39인지 여부 |
| `source` | 문자열 | 아니오 | `SYNTHETIC_REVIEWED`, `REAL_ANONYMIZED` 등 |
| `dataset_version` | 문자열 | 아니오 | `0.2` |

첫 베이스라인의 모델 입력은 `title + body`만 사용한다. `app_name`, `package_name`, `android_category`, `rule_score`는 데이터 분석과 오류 추적에는 사용하지만 모델 입력에서는 제외한다.

앱 이름과 규칙 점수를 모델 입력에 넣으면 특정 앱을 외우거나 규칙 신호를 이중 반영할 수 있기 때문이다.

v0.2 합성 데이터의 `package_name`은 실제 앱 패키지가 아닌 `synthetic.kr.*` 식별자를 사용한다. `rule_score`도 시나리오 설계상 기대값이며 Android 규칙 엔진을 직접 실행한 결과는 아니다. 실제 적용 전에는 Android 분류 결과와의 일치 검사를 별도로 추가한다.

## 5. 실제 알림 형태 반영 규칙

### 같은 앱에 두 라벨을 모두 포함한다

앱 이름만으로 정답을 맞히지 못하도록 하나의 앱에서 `PROMOTE`와 `KEEP` 사례를 함께 만든다.

| 앱 예시 | KEEP | PROMOTE |
|---|---|---|
| 쇼핑 앱 | 특가·쿠폰·추천 | 결제 실패·배송 예외·반품 기한 |
| 은행 앱 | 이벤트·상품 추천 | 이체 실패·이상 거래 확인 요청 |
| 배달 앱 | 할인·메뉴 추천 | 주문 취소·주소 확인 요청 |
| 학교 앱 | 일반 학사 소식 | 제출 마감·수강 변경 기한 |
| 업무 앱 | 주간 요약·공지 게시 | 승인·회신·회의 변경 요청 |

각 앱 또는 앱 계열에서 한 라벨이 70%를 넘지 않도록 한다.

### 제목을 지나치게 친절하게 만들지 않는다

다음 형태를 모두 포함한다.

- 제목이 앱 이름인 알림
- 제목이 짧은 알림: `알림`, `안내`, `확인해주세요`
- 본문에만 핵심 정보가 있는 알림
- 제목은 홍보처럼 보이지만 본문은 거래 상태인 알림과 그 반대 사례
- 금액, 시간, 주문번호, 말줄임표, 괄호, 이모지가 포함된 알림
- `광고`, `(광고)`, `[광고]`, `수신거부` 표기가 있는 알림과 없는 광고성 알림

### 최소 대조쌍을 만든다

한두 표현만 바뀌었을 때 라벨이 달라지는 문장을 포함한다.

```text
KEEP    오늘까지 사용할 수 있는 할인 쿠폰이 도착했어요
PROMOTE 오늘까지 결제 실패 건을 확인해주세요

KEEP    주문 상품을 추천해드려요
PROMOTE 주문이 취소되어 결제 수단을 확인해주세요
```

이 대조쌍 전체는 동일한 `template_group`으로 묶어 학습과 테스트에 나뉘지 않게 한다.

## 6. v0.2 초기 구성 목표

### 라벨이 있는 주 데이터 320개

- `model_eligible=true`: 240개
  - `PROMOTE`: 120개
  - `KEEP`: 120개
- 경계 밖 대조 데이터: 80개
  - 명확한 `IMPORTANT`: 40개
  - 명확한 `GENERAL`: 40개

### 문맥 의존 평가 데이터 80개

- 개인 메시지 및 단체 대화
- 개인 일정과 습관 알림
- 관심사 기반 콘텐츠와 커뮤니티 알림
- 발신자 또는 사용자의 상황 없이는 결정할 수 없는 알림

학습 성능의 주 지표는 `model_eligible=true`이면서 `clarity=CLEAR`인 행에서 계산한다.

## 7. 앱·상황 구성

다음 앱 계열을 고르게 포함한다.

- 은행·카드·간편결제
- 쇼핑·중고거래
- 택배·배달
- 지도·교통
- 학교·교육
- 회사·협업
- 병원·건강
- 공공기관
- 통신·구독
- 소셜·메신저
- 콘텐츠·게임
- 스마트홈·보안

특정 브랜드 표현은 현실성을 위한 예시로만 사용하고, 한 브랜드가 전체 데이터의 5%를 넘지 않게 한다.

## 8. 데이터 분할과 누수 방지

- 같은 `template_group`은 반드시 하나의 분할에만 포함한다.
- 숫자, 시간, 앱 이름만 바꾼 문장은 같은 템플릿으로 취급한다.
- 가능하면 일부 앱 계열 전체를 테스트에만 두는 별도 `unseen-app` 평가도 수행한다.
- 중복 정규화 문장과 제목·본문을 맞바꾼 준중복 문장을 검사한다.
- 합성 데이터와 실제 익명화 데이터의 성능을 따로 기록한다.

## 9. 품질 검사

v0.2 생성 후 다음 조건을 자동 검사한다.

- 필수 컬럼이 모두 존재한다.
- `CLEAR` 행의 `label`은 반드시 0 또는 1이다.
- `CONTEXT_DEPENDENT` 행은 기본 학습 대상에서 제외된다.
- `model_eligible=true`이면 `forced=false`, `rule_level=REVIEW`, `rule_score` 25~39를 모두 만족한다.
- 동일 앱 또는 앱 계열에 두 라벨이 모두 존재한다.
- `template_group`이 학습·테스트 양쪽에 중복되지 않는다.
- 제목과 본문이 모두 빈 행이 없다.
- 완전히 같은 제목과 본문이 중복되지 않는다.
- 라벨별, 앱 계열별, 알림 유형별 개수가 과도하게 치우치지 않는다.

## 10. v0.1과의 비교 원칙

v0.2 첫 실험에서는 모델 설정을 바꾸지 않는다.

```text
문자 n-gram: 2~5
TF-IDF min_df: 2
분류기: Logistic Regression
분할: StratifiedGroupKFold
```

모델을 그대로 둬야 데이터가 현실적으로 바뀐 효과만 비교할 수 있다. v0.2에서 정확도가 낮아지는 것은 실패가 아니라 평가가 현실적으로 어려워졌다는 신호일 수 있다.

## 11. 일정형 템플릿 확장 실험

초기 오류 분석에서 `optional_schedule`과 `schedule_change`가 전체 오분류의 대부분을 차지했다. 모델 설정과 전체 320개 행, REVIEW 라벨 120:120 균형은 유지하고, 두 일정 유형의 문장 구조만 라벨별 2개에서 5개로 확장했다.

| 지표 | 확장 전 | 확장 후 |
|---|---:|---:|
| Template Group | 12 | 18 |
| 5-Fold 정확도 | 76.7% | 87.9% |
| 전체 오분류 | 56 | 29 |
| False Positive | 40 | 20 |
| False Negative | 16 | 9 |
| Fold 정확도 표준편차 | 0.243 | 0.106 |

합성 데이터 안에서는 문장 구조 다양화가 특정 템플릿 암기를 줄이는 데 도움이 됐다. 다만 이 수치는 실제 사용자 알림 성능이 아니며, 실제 익명화 데이터나 별도의 외부 평가 세트로 다시 검증해야 한다.

## 12. 반복 분할 안정성 평가

한 번의 `random_state=42` 결과에만 의존하지 않도록 같은 모델과 데이터를 20개의 `random_state`로 반복 평가했다. 매 반복은 5-Fold `StratifiedGroupKFold`를 사용했고, 학습·평가 Template Group 중복은 모두 0개였다.

| 지표 | 결과 |
|---|---:|
| 반복 횟수 | 20회 |
| 평균 정확도 | 91.7% |
| 반복별 정확도 표준편차 | 0.026 |
| 최저 정확도 | 83.3% |
| 최고 정확도 | 95.0% |
| 90% 이상인 반복 | 17회 |

기존 `random_state=42`의 87.9%는 반복 평균보다 낮았다. 따라서 특정 분할에서만 우연히 얻은 최고 성능은 아니지만, 최저 정확도가 83.3%까지 내려가므로 데이터 그룹 구성의 영향은 여전히 남아 있다.
