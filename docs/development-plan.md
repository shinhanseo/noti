# 개발 계획

마지막 갱신: 2026-08-02

## 현재 상태 요약

`noti.`는 현재 알림 한 건이 `수집 → 필터링 → 중요도 판정 → Room 저장 → 홈 표시`되는 핵심 세로 흐름을 실기기에서 확인한 상태다.

완료된 핵심 범위는 다음과 같다.

- `NotificationListenerService`를 이용한 알림 수집
- 앱이 화면에 없거나 태스크가 제거된 상태에서의 알림 수집 확인
- 제목, 본문, 패키지명, 게시 시각, 카테고리 파싱
- 자기 앱 알림, 그룹 요약, 빈 알림 필터링
- Room을 이용한 알림, 중요도 결과, 판정 이유 저장
- 동일 알림 키의 갱신과 시스템 알림 제거 상태 기록
- 규칙 기반 중요도 정책 v1과 단위 테스트
- 중요 앱과 전역 중요 키워드의 DataStore 저장
- 저장된 사용자 설정을 알림 서비스의 실제 판정에 적용
- Hilt 기반 의존성 주입
- 온보딩, 알림 접근 권한, 중요 앱 선택, 중요 키워드 선택 화면
- 오늘 도착한 중요 알림을 구독해 표시하는 홈 화면의 기본 흐름
- 시스템 알림 창에서 지운 중요 알림도 `noti.` 홈에 유지
- Room 데이터의 클라우드 백업과 기기 전송 제외

아직 필요한 주요 범위는 다음과 같다.

- 알림 리스너 재연결 시 활성 알림 보충 수집
- 중요도 판정 이유 UI와 피드백 UI
- 마이페이지와 중요 앱별 제외 키워드 설정
- 전체 알림 목록, 필터, 바텀 내비게이션
- 앱 종류와 알림 형태에 따른 자연스러운 표시 문구 변환
- 온디바이스 모델 실험과 Android 연결
- 실기기 안정성, 성능, 개인정보 보호 최종 점검

## 구현 원칙

- 규칙 기반 중요도 판정은 항상 동작하는 기본 판정기로 유지한다.
- 온디바이스 모델은 규칙만으로 판단하기 애매한 `REVIEW` 알림만 보조한다.
- 모델을 Android에 연결하기 전에 데이터, 입력 계약, 평가 기준을 먼저 확정한다.
- 모델이 없거나 추론에 실패해도 규칙 기반 결과로 정상 동작해야 한다.
- 알림 제목과 본문은 외부 서버, 원격 AI API, 로그에 전송하거나 기록하지 않는다.
- 개인 알림 원문과 학습 데이터는 Git에 커밋하지 않는다.
- Room에는 원본 알림과 판정 결과를 분리해 저장하고, 화면용 문구 때문에 원본을 덮어쓰지 않는다.
- 각 단계는 빌드, 단위 테스트, 실기기 확인을 마친 뒤 다음 단계로 넘어간다.
- 화면 세부 디자인보다 수집, 판정, 저장, 피드백의 전체 흐름을 우선한다.

## 5단계: 온디바이스 AI 실험 — 다음 작업

### 5-1. 문제와 모델 계약 정의

- [ ] AI 호출 대상을 규칙 점수 `25~39`인 `REVIEW` 알림으로 제한
- [ ] 모델 입력 필드 확정
  - 정규화된 제목
  - 정규화된 본문
  - Android 알림 카테고리
  - 규칙 기반 점수
- [ ] 모델 출력 필드 확정
  - 중요 확률
  - 예측 등급
  - 점수 보정값
  - 모델 버전
- [ ] AI 점수 보정 범위와 최종 등급 계산 방식 확정

## 바로 다음 작업 순서

1. AI가 처리할 `REVIEW` 입력과 출력 계약을 문서로 확정한다.
2. `ml/` 디렉터리 구조와 개인정보 보호용 `.gitignore` 범위를 정한다.
3. 합성·비식별 예시 데이터로 작은 기준 데이터셋을 만든다.
4. TF-IDF와 Logistic Regression으로 기준 성능을 측정한다.
5. 중요 알림 Recall과 오탐 사례를 분석한다.
6. 기준 모델이 의미가 있을 때만 경량 모델과 ONNX 변환을 진행한다.
7. 모델 검증 이후 Android의 `REVIEW` 경로에 추론 인터페이스를 연결한다.

- 시간대별 체크인과 일일 브리핑
- 알림 요약
- 앱 전용 자연어 표시 템플릿 고도화
- 서버 동기화와 계정 기능
- 다른 기기의 알림 동기화

이 기능들은 핵심 수집, 판정, 피드백과 온디바이스 AI 흐름이 안정된 뒤 사용자 테스트 결과에 따라 우선순위를 결정한다.
