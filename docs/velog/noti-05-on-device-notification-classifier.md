# [noti. 05] 알림 중요도 판단에 LLM이 필요할까?

## 개요

`noti.`는 Android 기기에 도착한 알림 중 사용자가 지금 확인해야 할 알림을 찾아주는 앱이다.

현재는 `NotificationListenerService`로 알림을 수집하고, Room을 이용해 기기 내부에 저장하고 있다.

수집한 알림의 중요도는 먼저 설명 가능한 규칙을 이용해 계산한다.

예를 들어 다음과 같은 신호가 있으면 점수를 더하거나 뺀다.

```text
인증이나 보안과 관련된 표현      +30
결제·계정·예약의 중요한 상태 변화 +25
제출·답변·승인 등의 행동 요청     +20
광고·혜택·쿠폰 등의 홍보성 표현   -35
```

이 규칙으로 계산한 최종 점수는 다음 세 등급으로 나뉜다.

| 점수 | 등급 | 의미 |
|---:|---|---|
| 40 이상 | `IMPORTANT` | 중요한 알림 |
| 25~39 | `REVIEW` | 추가 판단이 필요한 알림 |
| 24 이하 | `GENERAL` | 일반 알림 |

처음에는 규칙만 잘 작성하면 중요한 알림을 충분히 찾을 수 있을 것이라고 생각했다.

하지만 규칙을 추가하면서 키워드만으로 판단하기 어려운 알림도 생겼다.

```text
오늘까지 회의 자료를 회신해주세요
```

이 알림은 날짜 표현과 행동 요청이 함께 있으므로 중요한 알림으로 판단하기 쉽다.

반면 다음 알림은 같은 표현이 들어 있어도 목적이 다르다.

```text
오늘까지 사용할 수 있는 할인 쿠폰을 확인하세요
```

`오늘까지`, `확인하세요`만 보면 빠르게 확인해야 할 알림처럼 보이지만 실제로는 홍보성 알림에 가깝다.

규칙을 계속 세분화할 수도 있다.

하지만 모든 문장 조합을 키워드와 정규식으로 미리 작성하는 데에는 한계가 있을 것이라고 생각했다.

그래서 규칙만으로 판단하기 애매한 알림에 한해 온디바이스 모델의 도움을 받으려고 한다.

이번 글에서는 다음 내용을 정리해 보려고 한다.

- AI가 중요도 정책의 어느 부분을 담당하는가?
- 이 기능에 LLM이 필요한가?
- 왜 서버가 아니라 기기 내부에서 실행하려고 하는가?
- 처음 비교할 세 가지 경량 분류 모델은 무엇인가?

---

## AI가 모든 알림을 판단하게 만들지는 않는다

처음 AI 모델을 알아볼 때에는 알림 제목과 본문을 모델에 입력하고, 모델이 최종 중요도를 결정하는 구조를 떠올렸다.

```text
알림
  ↓
AI 모델
  ↓
중요 또는 일반
```

하지만 이 구조에서는 사용자가 직접 지정한 설정까지 모델의 판단에 의해 바뀔 수 있다.

예를 들어 사용자가 특정 앱을 중요한 앱으로 설정했다면 그 설정은 모델보다 우선해야 한다.

반대로 중요한 앱에 `[광고]`를 제외 키워드로 추가했다면 모델이 중요하다고 판단하더라도 일반 알림으로 처리해야 한다.

현재 중요도 정책의 우선순위는 다음과 같다.

```text
현재 알림에 대한 사용자의 직접 수정
> 전역 중요 키워드
> 중요 앱별 제외 키워드
> 중요 앱
> 자동 점수
> 온디바이스 모델의 보조 점수
```

따라서 모델은 사용자 설정이나 기존 규칙을 대체하지 않는다.

다음 조건을 모두 만족할 때만 모델을 실행한다.

```text
사용자 강제 판정이 없다.
규칙 점수가 25~39점이다.
현재 등급이 REVIEW다.
```

규칙만으로 이미 명확한 결과에는 모델을 실행하지 않는다.

```text
40점 이상 → 규칙 결과 유지
24점 이하 → 규칙 결과 유지
25~39점   → 모델의 보조 판단 사용
```

모델이 추가하거나 차감할 수 있는 점수도 최대 15점으로 제한한다.

| 모델이 예측한 중요 확률 | 보조 점수 |
|---:|---:|
| 0.80 이상 | +15 |
| 0.65~0.79 | +10 |
| 0.35~0.64 | 0 |
| 0.20~0.34 | -10 |
| 0.20 미만 | -15 |

예를 들어 규칙 점수가 25점인 알림이 있다고 해 보자.

```text
규칙 점수 = 25
모델 중요 확률 = 0.84
모델 보조 점수 = +15

최종 점수 = 40
최종 등급 = IMPORTANT
```

모델의 판단이 확실하지 않다면 점수를 변경하지 않는다.

```text
규칙 점수 = 30
모델 중요 확률 = 0.52
모델 보조 점수 = 0

최종 점수 = 30
최종 등급 = REVIEW
```

이 구조의 목적은 AI에게 모든 판단을 맡기는 것이 아니다.

> 규칙으로 판단하기 애매한 좁은 구간에서만 제한된 보조 점수를 받는 것이 목적이다.

모델이 없거나 실행 중 오류가 발생해도 규칙 점수는 그대로 남는다.

모델 실패 때문에 알림 자체가 저장되지 않는 구조도 피하려고 한다.

## 이 문제는 생성이 아니라 분류다

요즘 AI라는 단어를 들으면 먼저 ChatGPT와 같은 LLM을 떠올리기 쉽다.

나도 처음에는 알림 내용을 모델에게 전달하고 다음과 같이 질문하는 방식을 생각했다.

```text
다음 알림이 지금 확인해야 할 중요한 알림인지 판단해줘.

제목: 회의 자료 요청
본문: 오늘 오후 3시까지 회신해주세요.
```

LLM이라면 다음과 같은 문장을 생성할 수 있다.

```text
마감 시간과 회신 요청이 포함되어 있으므로 중요한 알림입니다.
```

하지만 현재 `noti.`에 필요한 출력은 긴 설명 문장이 아니다.

```text
입력
- 알림 제목
- 알림 본문

출력
- 중요할 확률 0.0~1.0
```

즉, 해결하려는 문제는 다음과 같은 이진 분류 문제다.

```text
1 = 지금 확인해야 할 중요한 알림
0 = 지금 확인하지 않아도 되는 일반 알림
```

LLM은 문장을 생성하거나 질문에 답하고, 여러 단계의 지시를 처리할 수 있다.

반면 현재 필요한 기능은 하나의 짧은 문장을 두 범주 중 하나로 분류하는 것이다.

```text
텍스트 생성 모델
알림 → 설명 문장 생성

텍스트 분류 모델
알림 → 중요 확률 하나 출력
```

생성 기능을 사용하지 않는데도 LLM을 탑재하면 다음 부담이 생긴다.

- 모델 파일이 커질 수 있다.
- 실행 시 더 많은 메모리가 필요하다.
- 첫 로딩과 추론 시간이 길어질 수 있다.
- 배터리 사용량이 늘어날 수 있다.
- 출력 형식을 항상 일정하게 유지하기 위한 추가 처리가 필요하다.

현재 모델은 최종 결정을 내리는 역할도 아니다.

`REVIEW` 구간에 최대 15점을 더하거나 빼는 보조 역할만 수행한다.

이 역할을 위해서는 LLM보다 경량 텍스트 분류 모델이 더 적합하다고 판단했다.

## 온디바이스로 실행하려는 이유

알림 제목과 본문에는 민감한 정보가 포함될 수 있다.

예를 들면 다음과 같다.

- 개인 메시지
- 인증번호
- 결제 내역
- 계좌와 카드 정보
- 일정과 장소
- 배송 정보
- 회사 업무 내용

서버 기반 모델을 사용하면 알림 내용을 네트워크를 통해 외부로 전송해야 할 수 있다.

`noti.`는 처음부터 알림 제목과 본문을 기기 내부에서만 사용한다는 원칙을 두고 있다.

따라서 모델 추론도 기기 내부에서 수행하려고 한다.

```text
알림 수신
  ↓
기기 내부에서 규칙 점수 계산
  ↓
REVIEW일 때만 기기 내부 모델 실행
  ↓
Room에 결과 저장
```

온디바이스 방식에는 개인정보 보호 외에도 다음 장점이 있다.

- 인터넷 연결이 없어도 실행할 수 있다.
- 서버 요청을 기다릴 필요가 없다.
- API 사용 비용이 발생하지 않는다.
- 알림을 외부로 전송하기 위한 별도 동의와 보안 처리가 줄어든다.

대신 앱에 직접 모델을 포함해야 하므로 다음 조건을 고려해야 한다.

- 모델 파일이 너무 크지 않은가?
- 앱의 메모리 사용량이 크게 증가하지 않는가?
- 백그라운드에서 빠르게 실행할 수 있는가?
- 한국어의 조사와 띄어쓰기 변화를 처리할 수 있는가?
- Android에 적용하기 어렵지 않은가?
- 양자화 이후에도 정확도가 유지되는가?

결국 정확도가 가장 높은 모델 하나를 찾는 문제가 아니었다.

> 정확도, 모델 크기, 실행 시간, Android 적용 난이도를 함께 비교해야 하는 문제였다.

---

## 어떤 모델을 공부해 볼까?

온디바이스 텍스트 분류 모델을 찾아보니 생각보다 많은 후보가 있었다.

`fastText`, `DistilKoBERT`, `KoELECTRA`, `MobileBERT`, `TextCNN`, `LSTM`처럼 이름도 구조도 다른 모델이 나왔다.

하지만 아직 각 모델을 직접 학습하거나 Android에서 실행해 본 것은 아니다.

이 상태에서 모델의 장단점을 자세히 설명하거나 어떤 모델이 더 좋다고 결론 내리는 것은 순서가 맞지 않다고 생각했다.

우선 다음 조건을 기준으로 공부할 범위만 좁히려고 한다.

```text
Android 앱에 실제로 적용할 수 있어야 한다.
기기 내부에서 실행할 수 있어야 한다.
모델 크기가 지나치게 크지 않아야 한다.
한국어의 짧은 알림을 분류할 수 있어야 한다.
처음 공부하는 입장에서 구현 난이도가 지나치게 높지 않아야 한다.
```

현재는 다음 세 가지 방향을 차례로 살펴보려고 한다.

| 순서 | 모델 | 확인하고 싶은 점 |
|---:|---|---|
| 1 | 문자 n-gram + Logistic Regression | 단순하고 가벼운 모델로 어느 정도까지 분류할 수 있을까? |
| 2 | Average Word Embedding + MLP | 작은 신경망은 첫 모델보다 얼마나 나아질까? |
| 3 | Char TextCNN | 문자의 순서와 짧은 표현을 학습하면 어떤 차이가 생길까? |

지금 단계에서는 세 모델의 이름과 비교 방향만 정했다.

각 모델의 원리와 실제 장단점은 직접 학습하고 결과를 확인한 뒤 정리하려고 한다.

## 한 편에서 하나의 모델만 다루려고 한다

처음에는 한 글에서 세 모델의 개념과 장단점을 모두 비교하려고 했다.

하지만 아직 직접 구현하지 않은 모델을 한꺼번에 설명하면 조사한 내용을 다시 옮기는 글에 가까워질 수 있다.

`noti.` 시리즈에서는 실제 개발 과정에서 이해한 내용을 기록하고 싶다.

그래서 다음 글부터는 하나의 모델을 한 편의 주제로 삼으려고 한다.

각 글은 다음 흐름으로 작성할 예정이다.

```text
이 모델을 선택한 이유
  ↓
필요한 개념 공부
  ↓
학습 데이터 준비
  ↓
Python으로 직접 구현
  ↓
모델 학습
  ↓
평가 결과 확인
  ↓
틀린 알림 분석
  ↓
Android 적용 가능성 확인
```

개념을 설명하는 데서 끝내지 않고 실제 코드와 결과를 함께 남기려고 한다.

예를 들어 다음 내용이 포함될 수 있다.

- 사용한 데이터의 개수와 중요·일반 비율
- 학습과 테스트 데이터를 나눈 방법
- 실제 학습 코드
- Precision과 Recall
- Confusion Matrix
- 잘못 분류한 가상의 알림 예시
- 모델 파일 크기
- 알림 한 건의 추론 시간
- Android 적용 과정에서 생긴 문제

실험하기 전의 예상과 실제 결과도 구분해서 작성해야 한다.

```text
실험 전
문자 기반 모델이 띄어쓰기 변화에 강할 것으로 예상했다.

실험 후
현재 테스트 데이터에서는 어떤 표현을 맞혔고,
어떤 표현을 계속 틀렸다.
```

직접 측정하기 전에는 특정 모델이 더 정확하거나 빠르다고 단정하지 않으려고 한다.

---

## 세 모델의 비교 조건도 같아야 한다

나중에 세 모델을 비교하려면 실험 조건이 같아야 한다.

서로 다른 데이터로 학습한 결과를 비교하면 모델의 차이인지 데이터의 차이인지 알기 어렵다.

따라서 다음 조건을 최대한 동일하게 유지하려고 한다.

- 동일한 학습 데이터
- 동일한 검증 데이터
- 동일한 테스트 데이터
- 동일한 중요·일반 라벨
- 동일한 입력 정보
- 동일한 Android 테스트 기기

비교 항목은 학습을 진행하면서 구체화할 예정이다.

현재는 최소한 다음 내용을 확인하려고 한다.

```text
중요한 알림을 얼마나 놓치지 않았는가?
일반 알림을 중요하다고 과하게 판단하지 않았는가?
모델 파일은 얼마나 큰가?
알림 한 건을 판단하는 데 얼마나 걸리는가?
Android에 적용하는 과정은 얼마나 복잡한가?
```

정확도 하나만으로 최종 모델을 정하지는 않을 생각이다.

정확도가 조금 높더라도 모델이 지나치게 크거나 Android 적용이 복잡하다면 실제 앱에는 더 단순한 모델이 적합할 수 있다.

## 모델은 먼저 그림자 모드로 검증한다

모델을 학습했다고 바로 중요도 점수에 반영하지는 않는다.

먼저 모델의 결과를 저장만 하고 실제 등급에는 반영하지 않는 그림자 모드를 사용하려고 한다.

```text
규칙 점수 계산
  ↓
모델 중요 확률 계산
  ↓
예측 결과만 저장
  ↓
실제 중요도 등급에는 반영하지 않음
```

그림자 모드를 통해 모델이 어떤 알림을 맞히고 틀리는지 충분히 확인한 뒤 보조 점수를 적용한다.

모델이 없거나 실행에 실패하면 기존 규칙 결과를 그대로 사용한다.

모델 실패 때문에 알림 수집과 저장이 실패해서는 안 된다.

---

## 실제 알림 원문은 글과 저장소에 사용하지 않는다

모델을 학습하려면 알림 문장과 중요 여부가 표시된 데이터가 필요하다.

하지만 실제 알림에는 개인 메시지, 인증번호, 결제 내역과 같은 민감한 정보가 포함될 수 있다.

따라서 블로그와 공개 저장소에는 실제 알림 원문을 사용하지 않는다.

글에서 설명할 예시는 다음처럼 직접 만든 문장을 사용하려고 한다.

```csv
title,body,label
과제 제출 안내,보고서를 오늘까지 제출해주세요,1
쿠폰 도착,오늘만 사용할 수 있는 할인 쿠폰입니다,0
```

연습용 문장으로 학습 과정을 구현할 수는 있지만 그 결과를 실제 성능으로 해석해서는 안 된다.

실제 적용 가능성은 별도로 수집하고 라벨링한 데이터에서 검증해야 한다.

## 이번에 이해한 점

### AI를 도입한다고 기존 규칙을 버리는 것은 아니다

현재 모델은 사용자 설정과 규칙 기반 정책을 대체하지 않는다.

규칙이 애매한 `REVIEW` 구간에서만 최대 15점을 보조한다.

### 알림 중요도 판단은 생성보다 분류에 가깝다

필요한 출력은 설명 문장이 아니라 중요 확률 하나다.

따라서 첫 단계부터 LLM을 사용할 필요는 없다고 판단했다.

### 온디바이스 모델은 정확도만 보고 선택할 수 없다

알림 내용은 민감한 데이터이므로 기기 내부에서 처리하려고 한다.

모델 정확도뿐 아니라 파일 크기, 메모리, 추론 시간, 배터리와 Android 적용 난이도를 함께 비교해야 한다.

### 가장 복잡한 모델부터 시작할 필요는 없다

문자 n-gram과 Logistic Regression부터 직접 학습해 보고, 이후 Average Word Embedding과 Char TextCNN을 같은 조건에서 확인하려고 한다.

가벼운 모델로 충분하다면 Transformer를 추가하지 않아도 된다.

### 모델을 이해하려면 직접 학습하고 틀린 결과까지 봐야 한다

아직 직접 구현하지 않은 모델의 장단점을 먼저 나열하는 것보다, 하나의 모델을 학습하고 결과를 확인한 뒤 이해한 내용을 정리하는 편이 맞다고 생각했다.

앞으로는 개념, 코드, 평가 수치와 잘못 분류한 사례를 한 편에 함께 기록하려고 한다.

## 다음 단계

첫 번째로 문자 n-gram과 Logistic Regression을 공부하려고 한다.

다음 글은 개념만 정리한 뒤 끝내지 않고 실제 학습 결과가 준비된 뒤 작성하려고 한다.

다음 내용을 하나의 흐름으로 다룰 예정이다.

```text
지도학습과 이진 분류 이해
  ↓
알림의 Feature와 Label 정의
  ↓
연습용 데이터 작성
  ↓
문자 n-gram과 TF-IDF 이해
  ↓
Logistic Regression 학습 코드 작성
  ↓
테스트 데이터로 결과 측정
  ↓
틀린 알림 직접 분석
```

글에는 실제 실행한 코드와 함께 Precision, Recall, Confusion Matrix 같은 결과값을 포함하려고 한다.

예상과 다른 결과가 나온다면 좋은 수치만 고르지 않고 왜 틀렸는지도 함께 기록할 생각이다.

그 과정을 마친 뒤 첫 번째 모델이 `noti.`의 온디바이스 보조 모델로 실제 적용 가능한지 판단해 보려고 한다.
